# 判断軸の優先順位ルール

設計判断・案比較・推奨案決定時は、以下の優先順位で判断軸を扱う。**特に「データ安全性に関わる機能」を開発者の都合で省略しない**。

## 優先順位

```
1. ユーザー体験 / セキュリティ / データ安全性    ← 最優先
2. 業務整合性 / 旧仕様整合性
3. 設計品質（保守性・拡張性・コードの一貫性）
4. 開発者の手間（実装コスト・複雑度・テスト工数） ← 最後の判断材料
```

## 1. ユーザー体験 / セキュリティ / データ安全性（最優先）

ユーザーの作業を保護し、データを破壊しない機能群:

- **楽観的ロック** — 同時編集時のデータ上書き防止
- **バリデーション** — 不正入力の拒否
- **認証 / 認可** — 権限制御
- **監査ログ / 操作ログ** — 変更履歴の追跡
- **トランザクション** — 一貫性保証
- **削除済みレコード処理** — 参照整合性
- **CSRF / XSS / SQL インジェクション等の脆弱性対策**

これらは「実装コスト微小だから入れる / 入れない」で判断しない。**ユーザー保護として必要かどうか**で判断する。

## 2. 業務整合性 / 旧仕様整合性

業務フローや既存運用との整合性。旧システムからの移行では「Q1 原則: 改善でないなら旧仕様を消さない」を適用。

## 3. 設計品質

保守性・拡張性・コードの一貫性。既存規約・パターンとの整合性。

## 4. 開発者の手間（最後の判断材料）

実装コスト・複雑度・テスト工数。**これらは推奨理由の主軸にしない、補足情報として扱う**。

## 適用上の注意

### 比較表の列順

各案を比較する際の列順は以下を推奨:

```
ユーザー影響 → セキュリティ → 業務整合性 → 設計品質 → ... → 実装コスト
```

開発者視点の列（「コード量」「テスト工数」「学習コスト」等）を **左寄せ・上位** に並べない。

### データ安全性機能を「不要」と独自判断しない

- 「業務シナリオが起きにくいから不要」
- 「発生確率が低いから保険不要」
- 「被害が軽微だから許容」

これらは **業務確認していない独自判断** になりやすい。発生確率や被害が不明な場合は **保険として有り** に倒す。

### 既存規約・パターンを機械的に踏襲して良い

「データ安全性に関わる機能」が既存規約で確立されている場合（例: `backend-controller.md` の楽観的ロック / 操作ログ規約）、新規 PR でも機械的に踏襲する。「この PR は性質が違うから外す」のような独自判断は慎重に。

### 「メリットは？」「必要あるの？」質問への正しい応答

ユーザーから推奨案の根拠を問われた際の対応:

- **「判断を変える要求」と取り違えない** — 根拠の精査要求として扱う
- **根拠を論理的に整理して説明** — 質問のたびに推奨を翻さない
- **根拠が論理的に薄ければ正直に認めて更新** — それは「翻す」ではなく「論理的更新」
- **判断軸の優先順位ベースで判断** — 開発者の手間を主軸にしていないか自問する
